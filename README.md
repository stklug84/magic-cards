# Magic Cards Knowledge Graph

[![Lint](https://github.com/stklug84/magic-cards/actions/workflows/lint.yml/badge.svg?event=pull_request)](https://github.com/stklug84/magic-cards/actions/workflows/lint.yml)
[![Validate knowledge graph](https://github.com/stklug84/magic-cards/actions/workflows/validate.yml/badge.svg)](https://github.com/stklug84/magic-cards/actions/workflows/validate.yml)
[![CodeQL](https://github.com/stklug84/magic-cards/actions/workflows/codeql.yml/badge.svg)](https://github.com/stklug84/magic-cards/actions/workflows/codeql.yml)

An OWL/RDF knowledge graph describing a personal Magic: The Gathering card
collection: the schema, per-set card individuals generated from a
[Moxfield](https://moxfield.com) collection export, card-to-card synergies,
and a catalog of reusable SPARQL queries. The graph is published as a
versioned bundle so it can be used outside this repository.

This is an independent, fan-made project. It is not produced by, endorsed by,
or affiliated with Wizards of the Coast LLC. Card data is sourced from
[Scryfall](https://scryfall.com) and
[Gatherer](https://gatherer.wizards.com) under their respective data
distribution policies, and made available under the
[Wizards of the Coast Fan Content Policy](https://company.wizards.com/en/legal/fancontentpolicy).

## Dependencies

The repository is deliberately light on dependencies; what you need depends
on which part you use:

| Component | Requirement | Needed for |
|-----------|-------------|------------|
| Graph tooling (`scripts/generate_individuals.py`, `scripts/mtgvalidate/`) | Python 3.12+ and `pip install "rdflib>=7,<8"` | Regenerating `sets/` and the two collection graphs from a Moxfield export and an MTG Arena collection snapshot; TTL/SPARQL/consistency validation |
| MTG Arena collection (`scripts/arena_collection.py`) | [`uv`](https://docs.astral.sh/uv/), Google Chrome and an Untapped.gg login (`uv run` installs Playwright from the script's inline metadata) | Pulling the MTG Arena collection the Untapped.gg Companion syncs, as the generator's second input |
| SPARQL queries (`queries/`) | [Apache Jena](https://jena.apache.org/) (`arq`, `riot`; Java 21+) | Running the query catalog, TTL syntax validation as done in CI |
| Released package (`magic-cards-tools`: the graph-bundle contract and the validators) | Python 3.12+ — **stdlib only**; the `validate` extra adds rdflib | Validating your own graphs against a published bundle |
| Simulator binaries (`mtg-simulate`, `mtg-selfplay`, `mtg-cr`) | None — prebuilt release binaries for Linux and macOS (x86_64 and arm64); the Linux ones link glibc dynamically and, from v0.4.1, run on any Linux with glibc 2.28 or newer (v0.4.0 needs 2.34, and 2.39 for `mtg-simulate` on arm64); building from source needs the Rust toolchain pinned in [`rust/rust-toolchain.toml`](./rust/rust-toolchain.toml) | Simulating Commander matchups over the graph, tuning the AI, inspecting the Comprehensive Rules coverage |
| `MagicCompRules-YYYYMMDD.txt` | Download from Wizards of the Coast; not distributed here | Referenced by ontology comments; the simulator validates its `#[rule]` annotations against it at startup |

## Repository layout

| Path | Description |
|------|-------------|
| [`MagicCardsOntology.ttl`](./MagicCardsOntology.ttl) | The schema: classes, object/datatype properties, card types, keyword actions and abilities, ability words, subtypes, formats, rarities, legality and ruling modelling, and the game platforms (paper, MTG Arena, Magic Online) printings are available on and formats are played on. Its keyword, ability word and subtype vocabularies follow the Comprehensive Rules effective 2026-11-06. |
| [`MagicCardIndividuals.ttl`](./MagicCardIndividuals.ttl) | Aggregator ontology that `owl:imports` one instance graph per set from `sets/`. Contains no individuals of its own. |
| [`MagicCardSynergies.ttl`](./MagicCardSynergies.ttl) | Instance graph of card-to-card synergy relations (`:amplifies`, `:enables`, `:hasSynergyWith`; the inverses `:isAmplifiedBy` and `:isEnabledBy` are implied) between the cards of the **paper** collection, derived mechanic by mechanic from the keyword actions, keyword abilities and ability words on its cards. |
| [`MagicArenaSynergies.ttl`](./MagicArenaSynergies.ttl) | The same for the **MTG Arena** collection, including its digital-only cards and mechanics (perpetual changes, seek, conjure, …). A deck is built from one collection, never from both, so the two synergy graphs are kept apart: each relates only cards its own collection holds, and `check_consistency.py` enforces it. |
| [`MagicCardCollection.ttl`](./MagicCardCollection.ttl) | Physical inventory (`:isHeldOn :PaperMagic`): one reified `CollectionEntry` per collected variant — that is, per distinct combination of printing, finish and condition — carrying the total quantity held in that variant. No valuation data is modelled or published. Generated by `scripts/generate_individuals.py collection` — do not edit manually. |
| [`MagicArenaCollection.ttl`](./MagicArenaCollection.ttl) | MTG Arena inventory (`:isHeldOn :MTGArena`): one `CollectionEntry` per owned printing — digital copies have neither finish nor condition — carrying the copies the account owns. Generated by `scripts/generate_individuals.py collection` — do not edit manually. |
| [`sets/`](./sets/) | One generated TTL file per set, each defining the card individuals collected in paper or on MTG Arena with characteristics, platform availability, MTG Arena identity (Arena ID, name, set code and — where Arena numbers the printing differently — collector number: the fields of Arena's import format `N Name (SET) number`), legalities in the paper and MTG Arena formats, and official rulings. Generated by `scripts/generate_individuals.py` — do not edit manually. |
| [`queries/`](./queries/) | Catalog of 73 reusable SPARQL 1.1 queries. See [`queries/README.md`](./queries/README.md) and [`queries/INDEX.md`](./queries/INDEX.md). |
| [`MagicSimulationAnnotations.ttl`](./MagicSimulationAnnotations.ttl) | Behavior hooks (`:hasBehaviorHook`) and AI threat weights (`:threatWeight`) — house-authored opinion, kept separate from the generated card facts. |
| [`scripts/`](./scripts/) | Generator tooling, the MTG Arena collection tool (`arena_collection.py`, package `mtgarena/`), the graph-bundle builder (`build_graph_bundle.py`), and the Python packages released as `magic-cards-tools`: the graph validators (`mtgvalidate/`) and the graph-bundle contract plus behavior-key whitelist they share with the simulator (`mtgcards/`). |
| [`rust/`](./rust/) | The simulator: a Cargo workspace whose binaries (`mtg-simulate`, `mtg-selfplay`, `mtg-cr`) read the graph, play CR-grounded Commander matchups, tune the AI profiles and report the Comprehensive Rules coverage of the engine. |
| `collection.csv` | Moxfield collection export; input to the generator. Local and untracked (it contains private data such as purchase prices) — not distributed with the repository. |
| `arena-collection.json` | MTG Arena collection snapshot, pulled from Untapped.gg by `scripts/arena_collection.py` (with a Moxfield CSV and an Arena-format list next to it); input to the generator. Local and untracked, like `collection.csv`. |
| [`arena-picks.json`](./arena-picks.json) | Printings of the MTG Arena collection picked by hand where no lookup decides; read by `scripts/arena_collection.py`. |
| `catalog-v001.xml` | Generated OASIS XML catalog mapping the graph's `urn:` ontology IRIs to local files for ROBOT/Protégé. Untracked — regenerate with `python3 scripts/generate_catalog.py`. |
| `MagicCompRules-*.txt` | Magic: The Gathering Comprehensive Rules text referenced by ontology comments. |

## Importing a Moxfield collection

The graph's card data is generated from two inputs: a Moxfield collection
export of the paper collection saved as `collection.csv`, and a snapshot of
the MTG Arena collection that `scripts/arena_collection.py pull` writes to
`arena-collection.json` (see
[Importing the MTG Arena collection](#importing-the-mtg-arena-collection)),
both in the repository root. They are local and untracked — they contain
private data and are never distributed with the repository — so importing
is always a local workflow. Every printing either collection holds becomes
one card individual.

**1. Export from Moxfield.** In your Moxfield collection, choose the CSV
export. Save it as `collection.csv` in the repository root. The export has
the following header, and the generator reads the columns marked below:

```csv
"Count","Tradelist Count","Name","Edition","Condition","Language","Foil","Tags","Last Modified","Collector Number","Alter","Proxy","Purchase Price"
```

| Column | Used for |
|--------|----------|
| `Count` | Number of copies; summed across every row of the same printing, finish and condition |
| `Name` | Card name, used to resolve the printing via Scryfall |
| `Edition` | Set code, lowercased for the Scryfall lookup |
| `Collector Number` | Together with `Edition`, identifies the exact printing |
| `Condition` | `Near Mint`, `Lightly Played`, `Moderately Played`, `Heavily Played`, `Damaged` |
| `Language` | `English` or `German` |
| `Foil` | Empty (nonfoil), `foil`, or `etched` |

`Tradelist Count`, `Tags`, `Last Modified`, `Alter`, `Proxy` and
`Purchase Price` are ignored — the graph models no valuation data.
A row whose `Condition`, `Language` or `Foil` value falls outside the sets
listed above fails the import rather than being silently dropped.

Rows are grouped into collected variants: several acquisitions of the same
printing in the same finish and condition describe one physical stack, so
they become a single `CollectionEntry` whose quantity is their total. A
printing owned in both foil and non-foil keeps one entry per finish. Entry
IRIs are built from those attributes (`:SolRing…EntryFoilNearMint`), so
adding a lot in a new finish or condition never renames an existing entry.

**2. Generate the graph.**

```sh
python3 scripts/build_vocab.py                      # extract vocabulary + master card list from the ontology
python3 scripts/generate_individuals.py fetch       # resolve printings via the Scryfall API (cached)
python3 scripts/generate_individuals.py generate    # emit sets/*.ttl and /tmp/imports.json
python3 scripts/generate_individuals.py collection  # emit both collection graphs (needs no network)
python3 scripts/update_imports.py                   # rewrite the owl:imports block of MagicCardIndividuals.ttl
```

Every step but `collection` needs both inputs: `generate` rewrites every
set file, so a run without the Arena snapshot would drop the card
individuals only the MTG Arena collection holds — the generator stops
instead. The `collection` step resolves card individuals from the existing
`sets/*.ttl` files, so it can run standalone after any inventory change —
re-export and re-run just that step when only quantities, finishes or
conditions changed (it still reads both inputs and writes both collection
graphs).

**3. Commit the result.** Commit the regenerated files (`sets/`,
`MagicCardCollection.ttl`, `MagicArenaCollection.ttl`,
`MagicCardIndividuals.ttl`) through a pull request; the validation workflow
gates them. There is no CI regeneration — the inventories never leave your
machine.

## Importing the MTG Arena collection

MTG Arena has no collection export: the client only copies decks to the
clipboard, its `Player.log` has not listed owned cards since August 2021,
and there is no official web view or API. The one copy a browser can reach
is the collection the [Untapped.gg Companion](https://mtga.untapped.gg/companion)
(Windows / macOS, runs next to the game) syncs to the Untapped.gg account,
whose collection page loads the whole collection with a single request.
[`scripts/arena_collection.py`](./scripts/arena_collection.py) (the
[`mtgarena`](./scripts/mtgarena/) package) drives a real Chrome on a
dedicated profile, opens that page and reads that one response.

Prerequisites: the Companion has synced the collection (it shows at
`mtga.untapped.gg/profile/…/collection`), Google Chrome, and
[`uv`](https://docs.astral.sh/uv/) (the script declares its one dependency,
Playwright, inline; Playwright attaches to the installed Chrome and downloads
no browser of its own).

```sh
uv run scripts/arena_collection.py login          # once: sign in to Untapped.gg in the Chrome window that opens, then quit it with Cmd+Q
uv run scripts/arena_collection.py probe          # signed in? which Arena account (name and id); the response's shape and card counts
uv run scripts/arena_collection.py pull --dry-run # fetch, resolve the cards, show what changed; write nothing
uv run scripts/arena_collection.py pull           # write arena-collection.json, .moxfield.csv and .txt
uv run scripts/arena_collection.py export         # offline: rewrite the CSV and TXT from the JSON
uv run scripts/arena_collection.py resolve        # no Untapped.gg: resolve the JSON's cards anew, rewrite all three files
```

Then run the pipeline above: `pull` writes the generator's input. `login`
opens a plain Chrome (without the remote-debugging switch, which makes
Google sign-in refuse) on the tool's own profile under
`~/.cache/mtga-collection/`; quit it with Cmd+Q, because Chrome only saves
cookies on a clean quit. The session cookie stays in Chrome, and the
account ids are cached in `~/.cache/mtga-collection/account.json` — nothing
from the account is written into the repository. If Untapped.gg links
several Arena accounts, pick one with `--player`; if the page stops
exposing the account, pass the collection URL once with `--profile-url`.
`probe` prints the Arena account's name and id, the scalar fields next to
the card list (such as its sync date) and the card counts, and saves a
record of field names and types only; keep its output out of public
issues.

The tool's profile is not Chrome's default one, so Chrome allows remote
debugging on it: `probe` and `pull` open a DevTools port on 127.0.0.1
while they run, and any program running as you could start Chrome on the
profile with debugging on and read its cookies. The tool therefore keeps
the Untapped.gg session the only login in the profile. `login` waits for
its window to quit, then deletes every Google, YouTube, Discord and
Twitch cookie from the profile; `--no-wait` returns at once and leaves
that to the next command. `probe` and `pull` delete those cookies again
when they start and before they quit. Untapped.gg keeps its own session,
so this costs a provider password only when you sign in again.

Each owned Arena card id (`grpid`) is resolved against Untapped's public
dump of Arena's card database and Scryfall's bulk data (Arena's `grpid` is
Scryfall's `arena_id`), both cached under `~/.cache/mtga-collection/catalog`
and refreshed at most every six hours. A Scryfall match is accepted only if
its name agrees with Arena's title — about 0.2 % of Scryfall's `arena_id`s
point at a different card — and printings Scryfall has not given an
`arena_id` yet (a set released in the last weeks) are matched by set code
and collector number under the same name check. Last comes the name alone,
when it is the only printing of that name in the set: Arena numbers some
promos `0`, and it files Alchemy cards under yearly codes (`Y23` … `Y26`)
that stand for several of Scryfall's Alchemy sets at once, so for those
codes every Scryfall set of type `alchemy` is searched. What remains is
"known to Arena only", listed after each run: rebalanced `A-` cards
Scryfall does not list, and promos it lists more than once in a set — those
are picked by hand in `arena-picks.json`.

| File | Tracked | Contents |
|------|---------|----------|
| `arena-collection.json` | no | One entry per owned printing: `arena_id`, `quantity`, Scryfall name / set / collector number / id where matched, Arena's own name / set / number, and `basic`, `digital`, `rebalanced` flags. Sorted by name, no timestamps or account data. The generator's input. |
| `arena-collection.moxfield.csv` | no | Moxfield's collection CSV (the 13 columns of `collection.csv`), tagged `mtga`; Scryfall-matched printings only, basic lands left out unless `--include-basics`, digital-only editions left out with `--exclude-digital`. |
| `arena-collection.txt` | no | Arena's own import format, `N Name (SET) num`, with Arena's set codes — what Arena-aware importers such as ManaBox read. |
| [`arena-picks.json`](./arena-picks.json) | yes | Printings picked by hand for cards the lookups cannot place, or place wrongly: a list of objects with the card's `arena_id`, its `name`, and the Scryfall `set` and `collector_number` as strings; other keys, such as a `note`, are ignored. `pull` and `resolve` apply a pick before any lookup and stop when it does not hold. |

`pull` refuses to write a collection that shrank (Arena collections only
grow, so a smaller one means a stale or partial Companion sync) unless
`--allow-shrink` is given, and it writes nothing when nothing changed.
`resolve` runs the resolution again on the cards the JSON already lists,
with the current card data and without Untapped.gg or Chrome — after a new
pick, or when Scryfall or the tool learns to match more printings.

The generator reads, per owned printing, the Scryfall set and collector
number (the printing's card individual) and MTG Arena's own card ID, name,
set code and collector number, and writes:

- one card individual per printing, shared with the paper collection when
  both hold it. Arena's identity wins over Scryfall's for these printings:
  Scryfall lacks the Arena ID of new sets and Alchemy printings, and Arena
  files Alchemy printings under yearly codes (`Y22`–`Y26`) and anthology
  reprints under their original set, with other collector numbers
  (`:arenaCollectorNumber`);
- `MagicArenaCollection.ttl`, a `Collection` held on MTG Arena
  (`:isHeldOn :MTGArena`) with one entry per printing. Digital copies have
  neither finish nor condition.

Left out are basic lands, which MTG Arena grants in any number, and the
printings the tool could not match to a Scryfall printing. Digital-only
printings — Alchemy cards, Arena-only sets and anthologies — are included;
their digital mechanics (seek, conjure, perpetual changes) are not part of
the Comprehensive Rules, so the generator notes them as unknown keywords.

Terms of service: Untapped.gg's terms contain a general "download, scrape"
clause, and Wizards' terms prohibit third-party tools in general (the
Companion itself is one). The tool reads only the account's own data, with
one page view per run, in a visible Chrome the user signed in to; the
sanctioned alternative is Untapped.gg's Premium "Export Collection to CSV".

## Running queries with Apache Jena `arq`

The queries under [`queries/`](./queries/) are standalone SPARQL 1.1 files that
run against the plain TTL files — no triple store or OWL reasoner required.
With [Apache Jena](https://jena.apache.org) installed (`brew install jena`,
or download the distribution and add its `bin/` to `PATH`), use `arq`.

`arq` does **not** follow the `owl:imports` chain in
`MagicCardIndividuals.ttl`, so pass every data file explicitly via repeated
`--data` flags (shell expansion covers the 163 set files):

```sh
arq --data MagicCardsOntology.ttl \
    --data MagicCardSynergies.ttl \
    --data MagicCardCollection.ttl \
    --data MagicArenaCollection.ttl \
    $(printf -- '--data %s ' sets/*.ttl) \
    --query queries/10_collection/01_collection_size.rq
```

Loading everything is always safe; strictly required per query family:

| Query section | Required `--data` files |
|---------------|-------------------------|
| 02, 04, 05, 06, 08 (cards, legality, printings, rulings, introspection) | `MagicCardsOntology.ttl`, `sets/*.ttl` |
| 03, 07, 11 (synergy traversal) | additionally the synergy graph of the collection the deck is built from: `MagicCardSynergies.ttl` (paper) or `MagicArenaSynergies.ttl` (MTG Arena) — load one, not both |
| 05 printings-per-card, 10 (collection inventory) | additionally `MagicCardCollection.ttl` and `MagicArenaCollection.ttl` |

Roughly half the catalog is scoped to a deck individual; those queries need
an instance graph that this repository does not ship, supplied as an extra
`--data` file. [`queries/INDEX.md`](./queries/INDEX.md) marks which ones.

**Output formats** — the default is an ASCII table; add
`--results=CSV|TSV|JSON|XML` for machine-readable output. The
`CONSTRUCT`/`DESCRIBE` queries in `07_graph_patterns/` emit Turtle instead,
and the `ASK` query prints a boolean.

**Retargeting parameters** — `arq` has no CLI variable binding; edit the
`VALUES` clause in the `.rq` file (or a copy). Ad-hoc queries can be passed
inline as the last positional argument instead of `--query`.

**Repeated querying** — to avoid re-parsing all TTL files on every
invocation, either pre-merge them once with `riot`:

```sh
riot --output=turtle MagicCardsOntology.ttl MagicCardSynergies.ttl \
     MagicCardCollection.ttl MagicArenaCollection.ttl sets/*.ttl > /tmp/magic-all.ttl
arq --data /tmp/magic-all.ttl --query queries/...
```

or load them into a persistent TDB2 store and query that:

```sh
tdb2.tdbloader --loc /tmp/magic-tdb MagicCardsOntology.ttl \
    MagicCardSynergies.ttl MagicCardCollection.ttl MagicArenaCollection.ttl \
    sets/*.ttl
tdb2.tdbquery --loc /tmp/magic-tdb \
    --query queries/05_sets_and_printings/05_printings_per_card.rq
```

No OWL reasoning is involved: inverse properties are not materialized, which
is why the synergy queries spell out both edge directions via property paths
(see [`queries/README.md`](./queries/README.md) for details and further
engines: rdflib, GraphDB, Stardog, Blazegraph).

## Using the graph outside this repository

The graph and the tooling are published as two **independently versioned
release artifacts**, so an external consumer pins a known-good pair instead
of tracking `main`:

| Artifact | Tag namespace | Built by | Contents |
|----------|---------------|----------|----------|
| `magic_cards_tools-X.Y.Z-py3-none-any.whl` | `v*` | [`release.yml`](./.github/workflows/release.yml) | the Python packages (the graph-bundle contract, the validators) — code only |
| `mtg-simulate-vX.Y.Z-<target>.tar.gz` | `v*` | [`release.yml`](./.github/workflows/release.yml) | the simulator binaries for one target triple, with a `.sha256` next to each archive |
| `magic-cards-graph-YYYY-MM-DD.tar.gz` | `graph-*` | [`release-graph.yml`](./.github/workflows/release-graph.yml) | the knowledge graph — data only |

The namespaces are separate because the two move at different rates: an
inventory update must not force a code version bump, and vice versa.

The bundle is built by
[`scripts/build_graph_bundle.py`](./scripts/build_graph_bundle.py) and
contains `MagicCardsOntology.ttl`, `MagicCardIndividuals.ttl`,
`MagicCardCollection.ttl`, `MagicArenaCollection.ttl`,
`MagicCardSynergies.ttl`, `MagicArenaSynergies.ttl`,
`MagicSimulationAnnotations.ttl`, `sets/`, `queries/`, and a
`GRAPH-MANIFEST.json`. Unpack it and point `MTG_GRAPH_ROOT` at the result:

```sh
curl -fsSL -o graph.tar.gz \
  https://github.com/stklug84/magic-cards/releases/download/graph-2026-11-24/magic-cards-graph-2026-11-24.tar.gz
mkdir -p .graph && tar xzf graph.tar.gz -C .graph --strip-components=1
export MTG_GRAPH_ROOT="$PWD/.graph"
```

The simulator binaries find the graph the same way (`MTG_GRAPH_ROOT`, or
`--graph-root`, else the checkout above the working directory) and need
the Comprehensive Rules text next to it, because every `#[rule]`
annotation is validated against it at startup:

```sh
target=aarch64-apple-darwin   # or x86_64-apple-darwin, x86_64-unknown-linux-gnu, aarch64-unknown-linux-gnu
curl -fsSLO "https://github.com/stklug84/magic-cards/releases/download/v0.5.0/mtg-simulate-v0.5.0-${target}.tar.gz"
curl -fsSLO "https://github.com/stklug84/magic-cards/releases/download/v0.5.0/mtg-simulate-v0.5.0-${target}.tar.gz.sha256"
shasum -a 256 -c "mtg-simulate-v0.5.0-${target}.tar.gz.sha256"
tar xzf "mtg-simulate-v0.5.0-${target}.tar.gz"
"./mtg-simulate-v0.5.0-${target}/mtg-simulate" deck1.txt deck2.txt --offline --games 20
```

### The contract: `GRAPH-MANIFEST.json`

```json
{
  "graph_schema": 1,
  "graph_version": "2026-11-24",
  "ontology_iri": "urn:stklug84:MagicCardsOntology:2026-02-27#",
  "cr_version": "20260925",
  "requires_tools": ">=0.4.0",
  "sets": 164,
  "card_individuals": 3510
}
```

- **`graph_schema`** is the only *enforced* key. It versions the predicate
  vocabulary the tooling extracts (`:cardName`, `:hasCardType`,
  `:entryCard`/`:quantity`, `:hasBehaviorHook`, …), independently of which
  cards the graph contains — it is bumped when that vocabulary changes, not
  when a set is added. The simulator checks it when it opens a graph root
  and refuses a mismatch, naming both versions (`mtgcards.graph` in Python
  and the `mtgcards` crate in Rust implement the same check).
- **`ontology_iri`** lets consumers assert the namespace instead of
  hardcoding the date-stamped IRI.
- **`cr_version`** identifies the Comprehensive Rules edition the graph's
  annotations were authored against. The CR text is **not redistributable**
  and is therefore not in the bundle: fetch it from Wizards into the graph
  root yourself.
- **`requires_tools`** is a lower bound and is *informational only* —
  enforcing a PEP 440 specifier would need the `packaging` distribution,
  and `mtgcards` is deliberately stdlib-only.

A graph root with no manifest (a plain checkout of this repository) is
always accepted, so in-repo use is unaffected.

### Validating your own graphs against a bundle

Graphs that live outside this repository can be checked with the same
validators, by naming the bundle and your own root together:

```sh
pip install "magic-cards-tools[validate]"
mtg-validate --check ttl --check consistency .graph .
```

Both roots are needed: `owl:imports` resolution and the undefined-term and
dangling-reference checks only pass when the ontology and the card
individuals your graphs reference are in scope.

## Validation

All Turtle files and SPARQL queries are validated in CI
([`.github/workflows/validate.yml`](./.github/workflows/validate.yml)):

- **TTL syntax** — every `.ttl` file is parsed with Apache Jena `riot --validate`.
- **TTL conventions** — [`scripts/validate_ttl.py`](./scripts/validate_ttl.py)
  checks the standard prefix block, exactly one `owl:Ontology` declaration per
  file, and that every `owl:imports` target resolves to a file in this repo.
- **SPARQL** — [`scripts/validate_sparql.py`](./scripts/validate_sparql.py)
  parses every `.rq` file as SPARQL 1.1, verifies the canonical `mc:` prefix,
  and checks that every `mc:` term referenced actually exists in the graph.
- **Graph consistency** — [`scripts/check_consistency.py`](./scripts/check_consistency.py)
  loads all TTL files into one graph and checks for undefined properties or
  classes, dangling individual references, malformed entries, and synergy
  relations that do not connect card individuals.

Run locally (requires Python 3.12+ and `pip install "rdflib>=7,<8"`):

```sh
python3 scripts/validate_ttl.py
python3 scripts/validate_sparql.py
python3 scripts/check_consistency.py
```

Those three entry points are thin wrappers that scan the repository root;
the checks themselves live in [`scripts/mtgvalidate/`](./scripts/mtgvalidate/)
and take arbitrary graph roots, which is what lets an external consumer run
them against a published bundle (see
[Using the graph outside this repository](#using-the-graph-outside-this-repository)).
Installed as the `validate` extra they are also available as one command:

```sh
mtg-validate .
```

## Development

Linting, testing, CI structure, and the contribution workflow are
documented in [`CONTRIBUTING.md`](./CONTRIBUTING.md). The Python tooling
under [`scripts/`](./scripts/) is linted with ruff (`select = ALL`),
`mypy --strict`, and bandit (configuration in
[`pyproject.toml`](./pyproject.toml)); the simulator under
[`rust/`](./rust/) with rustfmt, clippy (`all` + `pedantic`, warnings
denied), cargo-deny and a 90 % line-coverage gate.
