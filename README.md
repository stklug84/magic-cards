# Magic Cards Knowledge Graph

[![Lint](https://github.com/stklug84/magic-cards/actions/workflows/lint.yml/badge.svg?event=pull_request)](https://github.com/stklug84/magic-cards/actions/workflows/lint.yml)
[![Validate knowledge graph](https://github.com/stklug84/magic-cards/actions/workflows/validate.yml/badge.svg)](https://github.com/stklug84/magic-cards/actions/workflows/validate.yml)
[![CodeQL](https://github.com/stklug84/magic-cards/actions/workflows/codeql.yml/badge.svg)](https://github.com/stklug84/magic-cards/actions/workflows/codeql.yml)

An OWL/RDF knowledge graph describing a personal Magic: The Gathering card
collection: the schema, per-set card individuals generated from a
[Moxfield](https://moxfield.com) collection export, card-to-card synergies,
and a catalog of reusable SPARQL queries. The graph is published as a
versioned bundle so it can be used outside this repository.

This is an independent, fan-made project. It is not produced by, endorsed by,
or affiliated with Wizards of the Coast LLC. Card data is sourced from
[Scryfall](https://scryfall.com) and
[Gatherer](https://gatherer.wizards.com) under their respective data
distribution policies, and made available under the
[Wizards of the Coast Fan Content Policy](https://company.wizards.com/en/legal/fancontentpolicy).

## Dependencies

The repository is deliberately light on dependencies; what you need depends
on which part you use:

| Component | Requirement | Needed for |
|-----------|-------------|------------|
| Graph tooling (`scripts/generate_individuals.py`, `scripts/mtgvalidate/`) | Python 3.12+ and `pip install "rdflib>=7,<8"` | Regenerating `sets/` and `MagicCardCollection.ttl` from a Moxfield export; TTL/SPARQL/consistency validation |
| SPARQL queries (`queries/`) | [Apache Jena](https://jena.apache.org/) (`arq`, `riot`; Java 21+) | Running the query catalog, TTL syntax validation as done in CI |
| Released packages (`magic-cards-tools`) | Python 3.12+ — **stdlib only**; the `validate` extra adds rdflib | Using the graph outside this repository |
| `MagicCompRules-YYYYMMDD.txt` | Download from Wizards of the Coast; not distributed here | Referenced by ontology comments; the released packages validate their `@rule` annotations against it at import |

## Repository layout

| Path | Description |
|------|-------------|
| [`MagicCardsOntology.ttl`](./MagicCardsOntology.ttl) | The schema: classes, object/datatype properties, card types, keyword abilities, subtypes, formats, rarities, legality and ruling modelling. |
| [`MagicCardIndividuals.ttl`](./MagicCardIndividuals.ttl) | Aggregator ontology that `owl:imports` one instance graph per set from `sets/`. Contains no individuals of its own. |
| [`MagicCardSynergies.ttl`](./MagicCardSynergies.ttl) | Instance graph of card-to-card synergy relations (`:amplifies`, `:isEnabledBy`, `:hasSynergyWith`). |
| [`MagicCardCollection.ttl`](./MagicCardCollection.ttl) | Physical inventory: one reified `CollectionEntry` per collected variant — that is, per distinct combination of printing, finish and condition — carrying the total quantity held in that variant. No valuation data is modelled or published. Generated by `scripts/generate_individuals.py collection` — do not edit manually. |
| [`sets/`](./sets/) | One generated TTL file per set, each defining the collected card individuals with characteristics, format legalities and official rulings. Generated by `scripts/generate_individuals.py` — do not edit manually. |
| [`queries/`](./queries/) | Catalog of 70 reusable SPARQL 1.1 queries. See [`queries/README.md`](./queries/README.md) and [`queries/INDEX.md`](./queries/INDEX.md). |
| [`MagicSimulationAnnotations.ttl`](./MagicSimulationAnnotations.ttl) | Behavior hooks (`:hasBehaviorHook`) and AI threat weights (`:threatWeight`) — house-authored opinion, kept separate from the generated card facts. |
| [`scripts/`](./scripts/) | Generator tooling, the graph-bundle builder (`build_graph_bundle.py`), the graph validators (`mtgvalidate/`), and the Python packages released as `magic-cards-tools` (`mtgcards/`, `mtgrules/`, `mtgviz/`). |
| `collection.csv` | Moxfield collection export; input to the generator. Local and untracked (it contains private data such as purchase prices) — not distributed with the repository. |
| `catalog-v001.xml` | Generated OASIS XML catalog mapping the graph's `urn:` ontology IRIs to local files for ROBOT/Protégé. Untracked — regenerate with `python3 scripts/generate_catalog.py`. |
| `MagicCompRules-*.txt` | Magic: The Gathering Comprehensive Rules text referenced by ontology comments. |

## Importing a Moxfield collection

The graph's card data is generated from a single input: a Moxfield
collection export saved as `collection.csv` in the repository root. The CSV
is local and untracked — it contains private data and is never distributed
with the repository — so importing is always a local workflow.

**1. Export from Moxfield.** In your Moxfield collection, choose the CSV
export. Save it as `collection.csv` in the repository root. The export has
the following header, and the generator reads the columns marked below:

```csv
"Count","Tradelist Count","Name","Edition","Condition","Language","Foil","Tags","Last Modified","Collector Number","Alter","Proxy","Purchase Price"
```

| Column | Used for |
|--------|----------|
| `Count` | Number of copies; summed across every row of the same printing, finish and condition |
| `Name` | Card name, used to resolve the printing via Scryfall |
| `Edition` | Set code, lowercased for the Scryfall lookup |
| `Collector Number` | Together with `Edition`, identifies the exact printing |
| `Condition` | `Near Mint`, `Lightly Played`, `Moderately Played`, `Heavily Played`, `Damaged` |
| `Language` | `English` or `German` |
| `Foil` | Empty (nonfoil), `foil`, or `etched` |

`Tradelist Count`, `Tags`, `Last Modified`, `Alter`, `Proxy` and
`Purchase Price` are ignored — the graph models no valuation data.
A row whose `Condition`, `Language` or `Foil` value falls outside the sets
listed above fails the import rather than being silently dropped.

Rows are grouped into collected variants: several acquisitions of the same
printing in the same finish and condition describe one physical stack, so
they become a single `CollectionEntry` whose quantity is their total. A
printing owned in both foil and non-foil keeps one entry per finish. Entry
IRIs are built from those attributes (`:SolRing…EntryFoilNearMint`), so
adding a lot in a new finish or condition never renames an existing entry.

**2. Generate the graph.**

```sh
python3 scripts/build_vocab.py                      # extract vocabulary + master card list from the ontology
python3 scripts/generate_individuals.py fetch       # resolve printings via the Scryfall API (cached)
python3 scripts/generate_individuals.py generate    # emit sets/*.ttl and /tmp/imports.json
python3 scripts/generate_individuals.py collection  # emit MagicCardCollection.ttl (needs no network)
python3 scripts/update_imports.py                   # rewrite the owl:imports block of MagicCardIndividuals.ttl
```

The `collection` step resolves card individuals from the existing `sets/*.ttl`
files, so it can run standalone after any inventory change — re-export from
Moxfield and re-run just that step when only quantities, finishes or
conditions changed.

**3. Commit the result.** Commit the regenerated files (`sets/`,
`MagicCardCollection.ttl`, `MagicCardIndividuals.ttl`) through a pull
request; the validation workflow gates them. There is no CI regeneration —
the inventory CSV never leaves your machine.

## Running queries with Apache Jena `arq`

The queries under [`queries/`](./queries/) are standalone SPARQL 1.1 files that
run against the plain TTL files — no triple store or OWL reasoner required.
With [Apache Jena](https://jena.apache.org) installed (`brew install jena`,
or download the distribution and add its `bin/` to `PATH`), use `arq`.

`arq` does **not** follow the `owl:imports` chain in
`MagicCardIndividuals.ttl`, so pass every data file explicitly via repeated
`--data` flags (shell expansion covers the 81 set files):

```sh
arq --data MagicCardsOntology.ttl \
    --data MagicCardSynergies.ttl \
    --data MagicCardCollection.ttl \
    $(printf -- '--data %s ' sets/*.ttl) \
    --query queries/10_collection/01_collection_size.rq
```

Loading everything is always safe; strictly required per query family:

| Query section | Required `--data` files |
|---------------|-------------------------|
| 02, 04, 05, 06, 08 (cards, legality, printings, rulings, introspection) | `MagicCardsOntology.ttl`, `sets/*.ttl` |
| 03, 07, 11 (synergy traversal) | additionally `MagicCardSynergies.ttl` |
| 05 printings-per-card, 10 (collection inventory) | additionally `MagicCardCollection.ttl` |

Roughly half the catalog is scoped to a deck individual; those queries need
an instance graph that this repository does not ship, supplied as an extra
`--data` file. [`queries/INDEX.md`](./queries/INDEX.md) marks which ones.

**Output formats** — the default is an ASCII table; add
`--results=CSV|TSV|JSON|XML` for machine-readable output. The
`CONSTRUCT`/`DESCRIBE` queries in `07_graph_patterns/` emit Turtle instead,
and the `ASK` query prints a boolean.

**Retargeting parameters** — `arq` has no CLI variable binding; edit the
`VALUES` clause in the `.rq` file (or a copy). Ad-hoc queries can be passed
inline as the last positional argument instead of `--query`.

**Repeated querying** — to avoid re-parsing all TTL files on every
invocation, either pre-merge them once with `riot`:

```sh
riot --output=turtle MagicCardsOntology.ttl MagicCardSynergies.ttl \
     MagicCardCollection.ttl sets/*.ttl > /tmp/magic-all.ttl
arq --data /tmp/magic-all.ttl --query queries/...
```

or load them into a persistent TDB2 store and query that:

```sh
tdb2.tdbloader --loc /tmp/magic-tdb MagicCardsOntology.ttl \
    MagicCardSynergies.ttl MagicCardCollection.ttl sets/*.ttl
tdb2.tdbquery --loc /tmp/magic-tdb \
    --query queries/05_sets_and_printings/05_printings_per_card.rq
```

No OWL reasoning is involved: inverse properties are not materialized, which
is why the synergy queries spell out both edge directions via property paths
(see [`queries/README.md`](./queries/README.md) for details and further
engines: rdflib, GraphDB, Stardog, Blazegraph).

## Using the graph outside this repository

The graph and the tooling are published as two **independently versioned
release artifacts**, so an external consumer pins a known-good pair instead
of tracking `main`:

| Artifact | Tag namespace | Built by | Contents |
|----------|---------------|----------|----------|
| `magic_cards_tools-X.Y.Z-py3-none-any.whl` | `v*` | [`release.yml`](./.github/workflows/release.yml) | the Python packages — code only |
| `magic-cards-graph-YYYY-MM-DD.tar.gz` | `graph-*` | [`release-graph.yml`](./.github/workflows/release-graph.yml) | the knowledge graph — data only |

The namespaces are separate because the two move at different rates: an
inventory update must not force a code version bump, and vice versa.

The bundle is built by
[`scripts/build_graph_bundle.py`](./scripts/build_graph_bundle.py) and
contains `MagicCardsOntology.ttl`, `MagicCardIndividuals.ttl`,
`MagicCardCollection.ttl`, `MagicSimulationAnnotations.ttl`, `sets/`,
`queries/`, and a `GRAPH-MANIFEST.json`. Unpack it and point
`MTG_GRAPH_ROOT` at the result:

```sh
curl -fsSL -o graph.tar.gz \
  https://github.com/stklug84/magic-cards/releases/download/graph-2026-08-09/magic-cards-graph-2026-08-09.tar.gz
mkdir -p .graph && tar xzf graph.tar.gz -C .graph --strip-components=1
export MTG_GRAPH_ROOT="$PWD/.graph"
```

### The contract: `GRAPH-MANIFEST.json`

```json
{
  "graph_schema": 1,
  "graph_version": "2026-08-09",
  "ontology_iri": "urn:stklug84:MagicCardsOntology:2026-02-27#",
  "cr_version": "20260619",
  "requires_tools": ">=0.2.0",
  "sets": 81,
  "card_individuals": 1393
}
```

- **`graph_schema`** is the only *enforced* key. It versions the predicate
  vocabulary the tooling extracts (`:cardName`, `:hasCardType`,
  `:entryCard`/`:quantity`, `:hasBehaviorHook`, …), independently of which
  cards the graph contains — it is bumped when that vocabulary changes, not
  when a set is added. `CardDatabase` checks it on construction and raises
  `mtgcards.graph.GraphSchemaError` on a mismatch, naming both versions.
- **`ontology_iri`** lets consumers assert the namespace instead of
  hardcoding the date-stamped IRI.
- **`cr_version`** identifies the Comprehensive Rules edition the graph's
  annotations were authored against. The CR text is **not redistributable**
  and is therefore not in the bundle: fetch it from Wizards into the graph
  root yourself.
- **`requires_tools`** is a lower bound and is *informational only* —
  enforcing a PEP 440 specifier would need the `packaging` distribution,
  and `mtgcards`/`mtgrules`/`mtgviz` are deliberately stdlib-only.

A graph root with no manifest (a plain checkout of this repository) is
always accepted, so in-repo use is unaffected.

### Validating your own graphs against a bundle

Graphs that live outside this repository can be checked with the same
validators, by naming the bundle and your own root together:

```sh
pip install "magic-cards-tools[validate]"
mtg-validate --check ttl --check consistency .graph .
```

Both roots are needed: `owl:imports` resolution and the undefined-term and
dangling-reference checks only pass when the ontology and the card
individuals your graphs reference are in scope.

## Validation

All Turtle files and SPARQL queries are validated in CI
([`.github/workflows/validate.yml`](./.github/workflows/validate.yml)):

- **TTL syntax** — every `.ttl` file is parsed with Apache Jena `riot --validate`.
- **TTL conventions** — [`scripts/validate_ttl.py`](./scripts/validate_ttl.py)
  checks the standard prefix block, exactly one `owl:Ontology` declaration per
  file, and that every `owl:imports` target resolves to a file in this repo.
- **SPARQL** — [`scripts/validate_sparql.py`](./scripts/validate_sparql.py)
  parses every `.rq` file as SPARQL 1.1, verifies the canonical `mc:` prefix,
  and checks that every `mc:` term referenced actually exists in the graph.
- **Graph consistency** — [`scripts/check_consistency.py`](./scripts/check_consistency.py)
  loads all TTL files into one graph and checks for undefined properties or
  classes, dangling individual references, malformed entries, and synergy
  relations that do not connect card individuals.

Run locally (requires Python 3.12+ and `pip install "rdflib>=7,<8"`):

```sh
python3 scripts/validate_ttl.py
python3 scripts/validate_sparql.py
python3 scripts/check_consistency.py
```

Those three entry points are thin wrappers that scan the repository root;
the checks themselves live in [`scripts/mtgvalidate/`](./scripts/mtgvalidate/)
and take arbitrary graph roots, which is what lets an external consumer run
them against a published bundle (see
[Using the graph outside this repository](#using-the-graph-outside-this-repository)).
Installed as the `validate` extra they are also available as one command:

```sh
mtg-validate .
```
