# Magic Cards Knowledge Graph

[![Lint](https://github.com/stklug84/magic-cards/actions/workflows/lint.yml/badge.svg?event=pull_request)](https://github.com/stklug84/magic-cards/actions/workflows/lint.yml)
[![Validate knowledge graph](https://github.com/stklug84/magic-cards/actions/workflows/validate.yml/badge.svg)](https://github.com/stklug84/magic-cards/actions/workflows/validate.yml)
[![CodeQL](https://github.com/stklug84/magic-cards/actions/workflows/codeql.yml/badge.svg)](https://github.com/stklug84/magic-cards/actions/workflows/codeql.yml)

An OWL/RDF knowledge graph describing a personal Magic: The Gathering card
collection — schema, per-set card individuals, synergies, and a catalog
of reusable SPARQL queries — plus the `magic-cards-tools` Python package:
a CR-grounded Commander matchup simulator built on the graph.

This is an independent, fan-made project. It is not produced by, endorsed by,
or affiliated with Wizards of the Coast LLC. Card data is sourced from
[Scryfall](https://scryfall.com) and
[Gatherer](https://gatherer.wizards.com) under their respective data
distribution policies, and made available under the
[Wizards of the Coast Fan Content Policy](https://company.wizards.com/en/legal/fancontentpolicy).

## Dependencies

The repository is deliberately light on dependencies; what you need depends
on which part you use:

| Component | Requirement | Needed for |
|-----------|-------------|------------|
| Matchup simulator (`scripts/simulate_matchup.py`, `mtgcards/`, `mtgrules/`) | Python 3.12+ — **stdlib only** | Running matches, statistics, unit tests |
| Simulator TUI (`mtgviz/`, `--watch` / `--replay`) | [`rich`](https://pypi.org/project/rich/) (`pip install rich`) — *optional* | Live/replay game visualization; both modes fall back to a plain-text viewer without it |
| Graph tooling (`generate_individuals.py`, `validate_ttl.py`, `validate_sparql.py`, `check_consistency.py`) | Python 3.12+ and `pip install "rdflib>=7,<8"` | Regenerating `sets/` from Scryfall, TTL/SPARQL/consistency validation |
| SPARQL queries (`queries/`) | [Apache Jena](https://jena.apache.org/) (`arq`, `riot`; Java 21+) | Running the query catalog, TTL syntax validation as done in CI |
| Rules-engine CR traceability | `MagicCompRules-YYYYMMDD.txt` in the repo root (download from Wizards of the Coast; not distributed here) | The simulator validates its `@rule` annotations against the official Comprehensive Rules text at import |

The simulator packages (`mtgcards`, `mtgrules`, `mtgviz`) are released as
the **`magic-cards-tools`** wheel/sdist on the
[Releases page](https://github.com/stklug84/magic-cards/releases)
(`pip install` the wheel; entry points `mtg-simulate` and `mtg-selfplay`).
The knowledge graph itself is not bundled — point the `MTG_GRAPH_ROOT`
environment variable at a checkout of this repository. Working from a
checkout needs no install: run the scripts directly as listed above.

## Repository layout

| Path | Description |
|------|-------------|
| [`MagicCardsOntology.ttl`](./MagicCardsOntology.ttl) | The schema: classes, object/datatype properties, card types, keyword abilities, subtypes, formats, rarities, legality and ruling modelling. |
| [`MagicCardIndividuals.ttl`](./MagicCardIndividuals.ttl) | Aggregator ontology that `owl:imports` one instance graph per set from `sets/`. Contains no individuals of its own. |
| [`MagicCardSynergies.ttl`](./MagicCardSynergies.ttl) | Instance graph of card-to-card synergy relations (`:amplifies`, `:isEnabledBy`, `:hasSynergyWith`). |
| [`MagicCardCollection.ttl`](./MagicCardCollection.ttl) | Physical inventory: one reified `CollectionEntry` per acquisition lot from `collection.csv`, carrying quantity, finish and condition. No valuation data is published — purchase prices stay in the local, untracked `collection.csv` (the ontology's `:purchasePrice` property is unused in the shipped graph). Generated by `scripts/generate_individuals.py collection` — do not edit manually. |
| [`sets/`](./sets/) | One generated TTL file per set, each defining the collected card individuals with characteristics, format legalities and official rulings. Generated by `scripts/generate_individuals.py` — do not edit manually. |
| [`queries/`](./queries/) | Catalog of 71 reusable SPARQL 1.1 queries. See [`queries/README.md`](./queries/README.md) and [`queries/INDEX.md`](./queries/INDEX.md). |
| [`MagicSimulationAnnotations.ttl`](./MagicSimulationAnnotations.ttl) | Simulation annotations: behavior hooks (`:hasBehaviorHook`) and AI threat weights (`:threatWeight`) consumed by the simulator — house-authored opinion kept separate from generated card facts. |
| [`scripts/`](./scripts/) | Generator and validation tooling, the shared card data layer (`mtgcards/`), the CR-grounded rules-engine matchup simulator (`mtgrules/`, built against `MagicCompRules-20260619.txt`), and the game visualization / TUI package (`mtgviz/`). |
| `collection.csv` | Source inventory of the physical collection; input to the generator. Local and untracked (contains private data such as purchase prices) — not distributed with the repository. |
| `catalog-v001.xml` | Generated OASIS XML catalog mapping the graph's `urn:` ontology IRIs to local files for ROBOT/Protégé. Untracked — regenerate with `python3 scripts/generate_catalog.py`. |
| `MagicCompRules-*.txt` | Magic: The Gathering Comprehensive Rules text referenced by ontology comments. |

## Running queries with Apache Jena `arq`

The queries under [`queries/`](./queries/) are standalone SPARQL 1.1 files that
run against the plain TTL files — no triple store or OWL reasoner required.
With [Apache Jena](https://jena.apache.org) installed (`brew install jena`,
or download the distribution and add its `bin/` to `PATH`), use `arq`.

`arq` does **not** follow the `owl:imports` chain in
`MagicCardIndividuals.ttl`, so pass every data file explicitly via repeated
`--data` flags (shell expansion covers the 80 set files):

```sh
arq --data MagicCardsOntology.ttl \
    --data MagicCardSynergies.ttl \
    --data MagicCardCollection.ttl \
    $(printf -- '--data %s ' sets/*.ttl) \
    --query queries/01_deck_inventory/01_list_all_decks.rq
```

Deck instance graphs (the deck-scoped query families operate on them) are
not part of this repository — add your own via additional `--data` flags.

Loading everything is always safe; strictly required per query family:

| Query section | Required `--data` files |
|---------------|-------------------------|
| 01, 02, 04, 05, 06, 09 (deck-scoped) | `MagicCardsOntology.ttl`, `sets/*.ttl`, plus your deck instance graphs |
| 03, 07, 09, 11 (synergy traversal) | additionally `MagicCardSynergies.ttl` |
| 05/05 printings-per-card, 10 (collection inventory) | `MagicCardsOntology.ttl`, `sets/*.ttl`, `MagicCardCollection.ttl` |
| 08 (introspection) | `MagicCardsOntology.ttl`, `sets/*.ttl` |

**Output formats** — the default is an ASCII table; add
`--results=CSV|TSV|JSON|XML` for machine-readable output. The
`CONSTRUCT`/`DESCRIBE` queries in `07_graph_patterns/` emit Turtle instead,
and the `ASK` query prints a boolean.

**Retargeting parameters** — `arq` has no CLI variable binding; edit the
`VALUES` clause in the `.rq` file (or a copy), e.g.
`VALUES ?deck { mc:SomeOtherDeck }`. Ad-hoc queries can be passed inline as
the last positional argument instead of `--query`.

**Repeated querying** — to avoid re-parsing all TTL files on every
invocation, either pre-merge them once with `riot`:

```sh
riot --output=turtle MagicCardsOntology.ttl MagicCardSynergies.ttl \
     MagicCardCollection.ttl sets/*.ttl > /tmp/magic-all.ttl
arq --data /tmp/magic-all.ttl --query queries/...
```

or load them into a persistent TDB2 store and query that:

```sh
tdb2.tdbloader --loc /tmp/magic-tdb MagicCardsOntology.ttl \
    MagicCardSynergies.ttl MagicCardCollection.ttl sets/*.ttl
tdb2.tdbquery --loc /tmp/magic-tdb \
    --query queries/05_sets_and_printings/05_printings_per_card.rq
```

No OWL reasoning is involved: inverse properties are not materialized, which
is why the synergy queries spell out both edge directions via property paths
(see [`queries/README.md`](./queries/README.md) for details and further
engines: rdflib, GraphDB, Stardog, Blazegraph).

## Regenerating set and collection files

Card individuals under `sets/` and the inventory graph
`MagicCardCollection.ttl` are generated from `collection.csv`. The CSV is a
local, untracked input (it contains private data and is not distributed with
the repository), so regeneration is a local workflow — restore your inventory
export to the repo root, then run:

```sh
python3 scripts/build_vocab.py                      # extract vocabulary + master card list from the ontology
python3 scripts/generate_individuals.py fetch       # resolve printings via the Scryfall API (cached)
python3 scripts/generate_individuals.py generate    # emit sets/*.ttl and /tmp/imports.json
python3 scripts/generate_individuals.py collection  # emit MagicCardCollection.ttl (needs no network)
python3 scripts/update_imports.py                   # rewrite the owl:imports block of MagicCardIndividuals.ttl
```

The `collection` step resolves card individuals from the existing `sets/*.ttl`
files, so it can run standalone after any inventory change in
`collection.csv`.

Commit the regenerated files (`sets/`, `MagicCardCollection.ttl`,
`MagicCardIndividuals.ttl`) through a pull request; the validation workflow
gates the result. There is no CI regeneration — the inventory CSV never
leaves your machine.

## Deck matchup simulation

[`scripts/simulate_matchup.py`](./scripts/simulate_matchup.py) runs Commander
games between 2–4 arbitrary deck files on a CR-grounded rules engine (stdlib
only; the optional TUI needs `pip install rich`). Two deck formats are
accepted: txt decklists (`N Card Name` lines, `//` comments, the commander
under a `// Commander` section header), whose card characteristics are
fetched by name from the [Scryfall API](https://scryfall.com/docs/api) with a
local cache (falling back to the knowledge graph offline; `--offline` skips
the lookups entirely), and `.ttl` deck
instance graphs (reified `:hasDeckEntry`/`:quantity` entries, commander via
`:isCommanderOf`), whose card characteristics come solely from the TTL
knowledge graph in [`sets/`](./sets/) — no network access. Cards outside the
collection can be supplied as additional card graphs via `--extra-cards`,
and opt-in custom-card overrides remain available (`--custom-cards`).
Deck files are yours to bring — none ship with this repository. The engine
lives in
[`scripts/mtgrules/`](./scripts/mtgrules/) (real stack and priority,
state-based actions, the layer system, replacement effects, Commander rules,
tunable AI policy profiles) on top of the
[`scripts/mtgcards/`](./scripts/mtgcards/) data layer (Wilson CIs, per-card
win-rate lift, multi-seed statistics, JSONL logs):

```sh
python3 scripts/simulate_matchup.py DECK1.txt DECK2.txt             # heads-up
python3 scripts/simulate_matchup.py DECK1.ttl DECK2.ttl \
    --extra-cards MyExternalCards.ttl                   # deck graphs, offline
python3 scripts/simulate_matchup.py a.txt b.txt c.txt --seeds 5     # pod,
                                                        # pooled over 5 seeds
python3 scripts/simulate_matchup.py DECK1.txt DECK2.txt --watch     # live TUI
python3 scripts/simulate_matchup.py DECK1.txt DECK2.txt \
    --games 3 --viz-file games.jsonl                    # record for replay
python3 scripts/simulate_matchup.py --replay games.jsonl --game 2   # replay
```

## Validation

All Turtle files and SPARQL queries are validated in CI
([`.github/workflows/validate.yml`](./.github/workflows/validate.yml)):

- **TTL syntax** — every `.ttl` file is parsed with Apache Jena `riot --validate`.
- **TTL conventions** — [`scripts/validate_ttl.py`](./scripts/validate_ttl.py)
  checks the standard prefix block, exactly one `owl:Ontology` declaration per
  file, and that every `owl:imports` target resolves to a file in this repo.
- **SPARQL** — [`scripts/validate_sparql.py`](./scripts/validate_sparql.py)
  parses every `.rq` file as SPARQL 1.1, verifies the canonical `mc:` prefix,
  and checks that every `mc:` term referenced actually exists in the graph.
- **Graph consistency** — [`scripts/check_consistency.py`](./scripts/check_consistency.py)
  loads all TTL files into one graph and checks for undefined properties or
  classes, dangling individual references, malformed deck entries, and synergy
  relations that do not connect card individuals.

Run locally (requires Python 3.12+ and `pip install "rdflib>=7,<8"`):

```sh
python3 scripts/validate_ttl.py
python3 scripts/validate_sparql.py
python3 scripts/check_consistency.py
```
