# Magic Cards Knowledge Graph

An OWL/RDF knowledge graph describing a personal Magic: The Gathering card
collection — schema, per-set card individuals, decks, synergies, and a catalog
of reusable SPARQL queries.

This is an independent, fan-made project. It is not produced by, endorsed by,
or affiliated with Wizards of the Coast LLC. Card data is sourced from
[Scryfall](https://scryfall.com) and
[Gatherer](https://gatherer.wizards.com) under their respective data
distribution policies, and made available under the
[Wizards of the Coast Fan Content Policy](https://company.wizards.com/en/legal/fancontentpolicy).

## Repository layout

| Path | Description |
|------|-------------|
| [`MagicCardsOntology.ttl`](./MagicCardsOntology.ttl) | The schema: classes, object/datatype properties, card types, keyword abilities, subtypes, formats, rarities, legality and ruling modelling. |
| [`MagicCardIndividuals.ttl`](./MagicCardIndividuals.ttl) | Aggregator ontology that `owl:imports` one instance graph per set from `sets/`. Contains no individuals of its own. |
| [`MagicCardSynergies.ttl`](./MagicCardSynergies.ttl) | Instance graph of card-to-card synergy relations (`:amplifies`, `:isEnabledBy`, `:hasSynergyWith`). |
| [`MagicCardCollection.ttl`](./MagicCardCollection.ttl) | Physical inventory: one reified `CollectionEntry` per acquisition lot from `collection.csv`, carrying quantity, finish, condition and purchase price. Generated by `scripts/generate_individuals.py collection` — do not edit manually. |
| [`MagicExternalCards.ttl`](./MagicExternalCards.ttl) | Card individuals referenced by deck graphs but not part of the physical collection (decks that do not belong to the collection owner), following the same modelling conventions as `sets/`. |
| [`sets/`](./sets/) | One generated TTL file per set, each defining the collected card individuals with characteristics, format legalities and official rulings. Generated by `scripts/generate_individuals.py` — do not edit manually. |
| [`decks/`](./decks/) | Deck instance graphs (currently the Saheeli, Radiant Creator Commander deck). |
| [`queries/`](./queries/) | Catalog of 71 reusable SPARQL 1.1 queries. See [`queries/README.md`](./queries/README.md) and [`queries/INDEX.md`](./queries/INDEX.md). |
| [`strategies/`](./strategies/) | Commander decklists built from the collection plus a Monte-Carlo matchup simulator. See [`strategies/README.md`](./strategies/README.md). |
| [`MagicSimulationAnnotations.ttl`](./MagicSimulationAnnotations.ttl) | Simulation annotations: behavior hooks (`:hasBehaviorHook`) and AI threat weights (`:threatWeight`) consumed by the simulator — house-authored opinion kept separate from generated card facts. |
| [`scripts/`](./scripts/) | Generator and validation tooling, the heuristic deck matchup simulator (`mtgsim/`), and a CR-grounded rules engine (`mtgrules/`, built against `MagicCompRules-20260227.txt`; run with `--engine rules`). |
| [`collection.csv`](./collection.csv) | Source inventory of the physical collection; input to the generator. |
| `MagicCompRules-*.txt` | Magic: The Gathering Comprehensive Rules text referenced by ontology comments. |

## Running queries with Apache Jena `arq`

The queries under [`queries/`](./queries/) are standalone SPARQL 1.1 files that
run against the plain TTL files — no triple store or OWL reasoner required.
With [Apache Jena](https://jena.apache.org) installed (`brew install jena`,
or download the distribution and add its `bin/` to `PATH`), use `arq`.

`arq` does **not** follow the `owl:imports` chain in
`MagicCardIndividuals.ttl`, so pass every data file explicitly via repeated
`--data` flags (shell expansion covers the 80 set files):

```sh
arq --data MagicCardsOntology.ttl \
    --data MagicCardSynergies.ttl \
    --data MagicCardCollection.ttl \
    --data MagicExternalCards.ttl \
    $(printf -- '--data %s ' sets/*.ttl decks/*.ttl) \
    --query queries/01_deck_inventory/01_list_all_decks.rq
```

Loading everything is always safe; strictly required per query family:

| Query section | Required `--data` files |
|---------------|-------------------------|
| 01, 02, 04, 05, 06, 09 (deck-scoped) | `MagicCardsOntology.ttl`, `sets/*.ttl`, `decks/*.ttl`, `MagicExternalCards.ttl` |
| 03, 07, 09, 11 (synergy traversal) | additionally `MagicCardSynergies.ttl` |
| 05/05 printings-per-card, 10 (collection inventory) | `MagicCardsOntology.ttl`, `sets/*.ttl`, `MagicCardCollection.ttl` |
| 08 (introspection) | `MagicCardsOntology.ttl`, `sets/*.ttl` |

**Output formats** — the default is an ASCII table; add
`--results=CSV|TSV|JSON|XML` for machine-readable output. The
`CONSTRUCT`/`DESCRIBE` queries in `07_graph_patterns/` emit Turtle instead,
and the `ASK` query prints a boolean.

**Retargeting parameters** — `arq` has no CLI variable binding; edit the
`VALUES` clause in the `.rq` file (or a copy), e.g.
`VALUES ?deck { mc:SomeOtherDeck }`. Ad-hoc queries can be passed inline as
the last positional argument instead of `--query`.

**Repeated querying** — to avoid re-parsing all TTL files on every
invocation, either pre-merge them once with `riot`:

```sh
riot --output=turtle MagicCardsOntology.ttl MagicCardSynergies.ttl \
     MagicCardCollection.ttl MagicExternalCards.ttl sets/*.ttl decks/*.ttl > /tmp/magic-all.ttl
arq --data /tmp/magic-all.ttl --query queries/...
```

or load them into a persistent TDB2 store and query that:

```sh
tdb2.tdbloader --loc /tmp/magic-tdb MagicCardsOntology.ttl \
    MagicCardSynergies.ttl MagicCardCollection.ttl MagicExternalCards.ttl sets/*.ttl decks/*.ttl
tdb2.tdbquery --loc /tmp/magic-tdb \
    --query queries/05_sets_and_printings/05_printings_per_card.rq
```

No OWL reasoning is involved: inverse properties are not materialized, which
is why the synergy queries spell out both edge directions via property paths
(see [`queries/README.md`](./queries/README.md) for details and further
engines: rdflib, GraphDB, Stardog, Blazegraph).

## Regenerating set and collection files

Card individuals under `sets/` and the inventory graph
`MagicCardCollection.ttl` are generated from `collection.csv`:

```sh
python3 scripts/generate_individuals.py fetch       # resolve printings via the Scryfall API (cached)
python3 scripts/generate_individuals.py generate    # emit sets/*.ttl and the owl:imports block
python3 scripts/generate_individuals.py collection  # emit MagicCardCollection.ttl (needs no network)
```

The `collection` step resolves card individuals from the existing `sets/*.ttl`
files, so it can run standalone after any inventory change in
`collection.csv`. Every printing referenced by the deck graphs is an
inventoried printing, so all deck cards are backed by collection entries.

## Deck matchup simulation

[`scripts/simulate_matchup.py`](./scripts/simulate_matchup.py) runs
Monte-Carlo Commander games between 2–4 arbitrary decklists (stdlib only, no
dependencies). Card characteristics are driven by the TTL knowledge graph in
[`sets/`](./sets/) and [`MagicExternalCards.ttl`](./MagicExternalCards.ttl),
with opt-in custom-card overrides (`--custom-cards`). The
engine lives in the modular [`scripts/mtgsim/`](./scripts/mtgsim/) package
(color-aware mana, multi-block combat, reaction windows, London mulligan,
tunable AI profiles, Wilson CIs, multi-seed statistics, JSONL logs):

```sh
python3 scripts/simulate_matchup.py DECK1.txt DECK2.txt             # heads-up
python3 scripts/simulate_matchup.py a.txt b.txt c.txt --seeds 5     # pod,
                                                        # pooled over 5 seeds
```

See [`strategies/README.md`](./strategies/README.md) for the decklist format,
architecture, statistics guide, and model assumptions.

## Validation

All Turtle files and SPARQL queries are validated in CI
([`.github/workflows/validate.yml`](./.github/workflows/validate.yml)):

- **TTL syntax** — every `.ttl` file is parsed with Apache Jena `riot --validate`.
- **TTL conventions** — [`scripts/validate_ttl.py`](./scripts/validate_ttl.py)
  checks the standard prefix block, exactly one `owl:Ontology` declaration per
  file, and that every `owl:imports` target resolves to a file in this repo.
- **SPARQL** — [`scripts/validate_sparql.py`](./scripts/validate_sparql.py)
  parses every `.rq` file as SPARQL 1.1, verifies the canonical `mc:` prefix,
  and checks that every `mc:` term referenced actually exists in the graph.
- **Graph consistency** — [`scripts/check_consistency.py`](./scripts/check_consistency.py)
  loads all TTL files into one graph and checks for undefined properties or
  classes, dangling individual references, malformed deck entries, and synergy
  relations that do not connect card individuals.

Run locally (requires Python 3.12+ and `pip install "rdflib>=7,<8"`):

```sh
python3 scripts/validate_ttl.py
python3 scripts/validate_sparql.py
python3 scripts/check_consistency.py
```
